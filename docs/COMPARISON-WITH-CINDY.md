# Rakko vs Cindy：实现对比

> 日期：2026-11-11
> 口径：我们 **7,638 行**（不含测试，49 个文件），Cindy Desktop **12,136 个文件**。
> 数据来源：本项目实际代码 + `makecindy/cindy` 文档（`pi-harness.md` 61KB、
> `maker-core-and-agent-behavior.md` 92KB、`cindy-bots-runtime.md` 137KB）。

---

## 零、先说结论

我们做的是 **Cindy 的一个垂直切片**，约等于它的 **5–8%**。

但切片选得对：核心链路（pi 集成 → 工具调用 → 权限审批 → 持久化）
在 7.6 千行内跑通了，而 Cindy 为此写了数十万行——因为它同时支持 3 个 harness、
4 个平台、几十种供应商形态、以及一整套商业化能力。

**一句话**：我们的胜负不在功能数量，在「同类事情能不能做得更简单」。
下面逐项对比，好话坏话都说。

---

## 一、逐项对比

### 1. key 隔离（**我们明显更好**）

| | Cindy | Rakko |
|---|---|---|
| key 存放 | spawn env（`CINDY_PI_API_KEY`）| **只在 CompatProxy 内存** |
| pi 进程能拿到 | 能（env 可见）| **不能，只有占位串** |
| 官方文档表述 | 「完全访问档下 token **可能被读取**」| 「Agent 读环境变量只能拿到占位串」 |

**证据**：Cindy `pi-harness.md:27-28` 原文承认这个风险。
我们的 `packages/proxy/src/server.ts` 在转发时替换 Authorization。

**代价**：多了 347 行 proxy + 一个进程内 HTTP 服务。
Cindy 不这么做是因为它要支持用户自带 OAuth 订阅、
供应商分享、多账号池——这些场景下 key 必须进 env 才能被上游 SDK 用。

**结论**：在「只支持用户自带 API key」这个窄场景下，我们的方案更干净。
一旦要支持 OAuth 订阅，这套设计就得重做。

---

### 2. 权限审批（**Cindy 深得多**）

| | Cindy | Rakko |
|---|---|---|
| 权限档 | `ask` / `bypassPermissions`（bridge 内两档，auto 在 Host 侧）| `ask` / `auto` / `bypassPermissions`（三档都在 bridge）|
| 拦截点 | `pi.on('tool_call')` 注入扩展 | 同 |
| 档位热切换 | 写文件，每次 tool_call 现读 | 同 |
| **自动审核** | `auto-review.ts` **367KB** | **无**（auto 与 ask 行为相同）|
| **凭证路径保护** | 三处同口径，几十条正则 | **无** |
| MCP 工具审批 | 有 | 无（还没做 MCP）|
| 控制面写入保护 | 有（agentHome 内写强制确认）| **有**（同样实现）|

**Cindy 强在哪**：`auto-review.ts` 367KB 不是虚的。
它要做命令解析、路径规范化、凭证路径识别、风险分级，
还要保证「三处判定同口径」——因为 bridge 是自包含的，不能 import，
所以同一套规则要维护三份。

**我们弱在哪**：`auto` 档名不副实。UI 上叫「自动审批」，
实际与「每次询问」完全一样。dogfood 一次改 bug 任务弹了 3 次审批。

**我们的取舍**：写明「P0 暂等同询问」，不假装它生效。
Cindy 的做法是把它做成真分类器——这是 3–5 人日的工作量，我们推迟了。

---

### 3. 会话管理（**Cindy 完胜**）

| | Cindy | Rakko |
|---|---|---|
| 会话持久化 | SQLite + 迁移 | SQLite + 迁移（**同**）|
| **空闲回收** | 30min TTL / 5min 扫描，`piIdleReleaseWatcher.ts` | **无** |
| **会话树 / 分支** | Pi entry tree + `session.treeRehydrate` 原子替换投影 | **无** |
| **fork / rewind** | 有 | 无 |
| **上下文续接** | `--resume` 接 pi 会话文件 | **无**（打开旧会话只能看历史，发消息时 pi 全新建）|
| 消息分页 | 有 | **有**（`beforeId` 往上翻）|

**最要命的缺口是「上下文续接」**：
用户打开昨天的会话，看到历史，发一句「继续说」——
pi 是全新建的，不记得之前聊过什么。

这个必须修，否则「会话持久化」只做了一半。

**空闲回收**我们也缺。现在 5 个会话一直开着就是 500MB。
Cindy 的记录说这是上游 issue #5830，他们专门做了 watcher。
我们的做法是关闭会话时回收（实测零泄漏），但没有「闲置自动回收」。

---

### 4. 工具链（**Cindy 完胜**）

| | Cindy | Rakko |
|---|---|---|
| 内置工具 | read/write/edit/bash/grep/find/ls/powershell | 用 pi 自带的（read/write/edit/bash/grep/find/ls）|
| 工具可观测 | 折叠块 + diff 视图 + 运行记录抽屉 | 折叠块（**有**）|
| 输出处理 | 大文本走文件路径、超大 body 落盘分块 | **ANSI 清理 + 32KB 截断**（dogfood 后加的）|
| worktree | 有 | 无 |
| Git 审查 | 有 | 无 |
| 成果复核 `/review` | 有 | 无 |

**我们做对的一点**：工具输出在**翻译层**统一清理，
不是散在各处。Cindy 因为要支持 3 个 harness，每个 translator 都要各自处理。

---

### 5. 模型接入（**各有取舍**）

| | Cindy | Rakko |
|---|---|---|
| 协议形态 | 四种全支持 | 只做 `openai-completions` |
| 供应商 | 几十家 + 订阅 + 分享 + 账号池 | 用户手填 baseUrl |
| compat 自愈 | 有（400 时移除缓存字段，学习 7 天）| **无** |
| 模型目录 | 服务端下发 | 内置预设 + 用户自定义 |
| cost 四字段校验 | 有 | **有**（同样踩过坑）|

**Cindy 的 compat 自愈值得抄**：某些上游拒收 `prompt_cache_key`，
收到 400 时移除这两个字段再试一次，成功后记 7 天。
我们没有这个，遇到不兼容的上游就是直接报错。

---

### 6. 扩展生态（**我们完全没有**）

| | Cindy | Rakko |
|---|---|---|
| 插件系统 | `.cindy` 沙箱 + 市场 | 无 |
| MCP | 完整（151 文件，2.7MB）| 无 |
| SkillHub | 有 | 无 |
| Hook 控制 | 有（1.6MB）| 无 |
| 伙伴（Teammate）| 6.9MB | 无 |

这些是 P2 的内容，不在当前范围。但要说清：**没有它们，Rakko 只是一个能对话的 GUI**。

---

### 7. 布局系统（**我们做了骨架，Cindy 完整**）

| | Cindy | Rakko |
|---|---|---|
| 递归 split/pane 树 | 有 | **有**（193 行 + 19 测试）|
| 面板注册表 | 有 | **有**（`panel-registry.ts`）|
| 持久化 | `LayoutStore.ts` | **有**（localStorage）|
| 未注册面板保留位置 | 有 | **有**（显示占位）|
| **拖拽分割** | 有 | **无**（fraction 只能代码改）|
| **边组停放机制** | 有（避免 webview 重载）| 无（还没 webview）|
| 页签组 | 有（`TAB_GROUP_IDS`）| 无 |

我们的布局树是**按 Cindy 的不变量写的**，但只实现了渲染与持久化，
交互层（拖拽、页签、停放）都没做。

## 二、我们做对了什么

### 1. 用实测替代文档

Cindy 的文档写了很多「应该」，我们每条都实测：

| 事项 | Cindy 文档说 | 我们实测发现 |
|---|---|---|
| `--append-system-prompt` 传文件路径 | 可以 | 可以，但**文件不存在时静默当字面文本** |
| `models.json` 的 cost | 四字段 | 缺一个 → **整个文件失效、所有模型消失** |
| 内联提示词上限 | 未量化 | 实测 **7,700 字符**就报「命令行太长」|
| Electron 里跑 pi | 用 `utilityProcess.fork` | `process.execPath` 是 electron.exe，**直接崩且无错误** |

这些写在 `AGENTS.md` 和注释里，后来都变成测试。

### 2. 把「失败」写进代码而不是注释

```ts
// fail-closed：读不到一律 ask
function readMode(): Mode { ... }
```
```ts
// 实测 pi 1.4.0：不存在的路径会静默当字面文本
await assertAppendPromptUsable(path);
```

每条都是踩过的坑，不是想象中的风险。

### 3. 测试密度更高

我们 **7,638 行代码 / 241 个测试**，约 1:0.032。
重点覆盖的是「实测踩过的坑」而不是覆盖率数字。

比如 `bridge-source.test.ts` 会检查**生成的扩展源码能不能被 JS 解析**——
因为那是一个模板字符串，写错一个转义就整段失效。

## 三、我们做错了什么

### 1. 布局树曾经是死代码

写完 193 行 + 19 个测试，但 `LayoutHost` 从没被 App 引用，
而且不存盘。**三个月后才在对比时发现。**

教训：**测了不等于用了**。应该有一条「集成测试」验证它真的在界面上。

### 2. auto 档名不副实

UI 上叫「自动审批」，实际不生效。虽然注释写了 P0 等同询问，
但**用户看不到注释**。

要么实现，要么改名叫「每次询问（自动审批待实现）」。

### 3. README 说过时的话，误导了 agent

dogfood 时 agent 照着 README 回答「还不能对话」，
而那时对话早就做完了。

教训：文档是 agent 的输入，**过时的文档比没有文档更糟**。

### 4. 没有空闲回收

Cindy 专门做了 `piIdleReleaseWatcher`，我们只是在关闭会话时回收。
用户开 5 个会话挂着不动 = 500MB。

### 5. 会话上下文没接续

这是最严重的功能缺口。持久化只做了一半。

---

## 四、如果只能改三件事

按「用户能感知到的伤害」排序：

**1. 会话上下文续接**（最高优先级）
打开旧会话说「继续说」，agent 一脸茫然。这是**功能承诺没兑现**。

**2. auto 档真分类器**
dogfood 一次改 bug 弹 3 次审批。真实使用会很烦。
或者先改名字，别骗人。

**3. 空闲回收**
照 Cindy 的 30min TTL 做，约 1 人日。

## 五、Cindy 值得抄但我们还没抄的

| 项 | 为什么值得 | 工作量 |
|---|---|---|
| **compat 自愈** | 上游拒收缓存字段时自动降级，用户体验差别很大 | 2 人日 |
| **空闲回收** | 直接解决内存累积 | 1 人日 |
| **凭证路径保护** | 防止 agent 读 `~/.ssh/id_rsa` 这类文件 | 1 人日 |
| **自动审核分类器** | 减少审批打扰 | 3–5 人日 |
| **会话树分叉** | 从一个问题分两条路探索 | 5 人日 |

---

## 六、不要抄的

| 项 | 理由 |
|---|---|
| 三 harness 抽象 | 只做 pi，抽象是负债 |
| 多端互联 / IM | 首期不做，架构已留口子 |
| 供应商分享 / 账号池 | 商业化能力，我们是本地应用 |
| 插件沙箱（`.cindy`） | 复杂度极高（128KB 规范），生态起来再说 |
| utilityProcess 跑 pi | 我们要直接操作 stdout，`utilityProcess` 反而绕远 |
